# 意思決定ログ — LINE不動産問い合わせエージェント

- 何のファイルか: 開発の経緯を時系列で残す番号付きの記録
- 使い方: 引き継ぎ書・仕様書・コードコメントにある「意思決定ログN」はこのファイルの N 番。新しい経緯は末尾に次の番号を振って追記する（並行セッションがあるときは、コミット直前に `git fetch` して origin と自分のブランチの最大＋1 を振る）
- いまの状態・次にやることは [引き継ぎ書](引き継ぎ書.md) に、仕様は [DESIGN.md](../DESIGN.md) に置く。ここには「いつ・何を・なぜそう決めたか」だけを書く

## 時系列（1 が最初）

1. **2026-10-07: 立ち上げ** — DESIGN.md（同日作成）に沿って、Next.js 16.4（App Router・TypeScript・Tailwind 4）一本で LINE Webhook と管理画面を同居させ、Supabase（Postgres・Auth・RLS）に状態を置き、Vercel に載せる。理由は 1 人で保守できる最小構成で追加インフラが要らないこと。LLM は Claude API（意図分類＋条件抽出は Haiku 級、回答生成は Sonnet 級）。テストは Vitest。業務ルールは `src/domain` の純関数に集約し、外部サービスはインターフェースの背後に置いて実キーなしでテストが通る形にする。リポジトリは github.com/KfkaK/line-rental-agent を非公開で作り、README と評価の数字が揃う Week 4 に公開へ切り替える（ユーザー判断）。設計書は `DESIGN.md` をルートに置いたまま仕様の正とし、別に詳細仕様は作らない
2. **2026-10-07: Week 1 の土台（実装で決めたこと）** — 共有の型契約を `src/domain/types.ts` に置き、中核（スロットの差分更新・優先順位つき検索・緩和提案・営業時間・1ターンの判断 `decideTurn`）をメインが純関数で書き、周辺（架空データ・DB 層・LINE・LLM の条件抽出）を Sonnet 4 本に並列で渡した。決めたこと: (1) **must の絞り込みは SQL の WHERE でなく、公開物件を全件取得して純関数で行う**。1社の物件は数百〜数千件で十分速く、緩和の試算も同じ関数で済み、DB なしでテストできるため。件数が増えたら同じ条件を SQL に移す (2) 並びは スコア降順 → 月額（家賃＋管理費）の安い順 → 物件 ID 昇順。予算は管理費込みの月額と比べる (3) 最寄り駅は `access`（駅と徒歩の組の配列）で持ち、徒歩はエリア条件の駅への徒歩で評価・表示する (4) 緩和で「できれば」に下げる候補からエリア・予算・徒歩を外し、従来型の幅の拡大（予算＋5,000円 → 徒歩＋5分 → 隣の駅）で扱う（エリア外・予算超えまで混ざると提案として不自然なため） (5) `unmatched` はそのまま表示できる不足の説明（「オートロックなし」「徒歩12分」） (6) **禁止トピックの引き継ぎでは AI の応答を止めない**。DESIGN.md の図は「AI自動応答を停止」、3.4 は「担当者の手動返信で停止」と食い違っていたので、夜間の一次対応を完結させる目的に合う後者に合わせ、質問は `conversations.handoff_notes` に残して朝の一覧に出す (7) 内見の候補日は翌営業日以降の営業日だけを受け、2件揃ったら仮受付する（1件でも「この日時で送る」で送れる） (8) 署名検証は加工前のバイト列で行い、`after()` の中の例外はルートで捕まえてログに出す。`maxDuration = 60` (9) Fable との壁打ちで、禁止トピックと条件変更が同じ発話にあると条件が捨てられる穴が見つかったので、条件を当てて引き継ぎ文に続けて検索結果を出すよう直し、引き継ぎメモに対象物件 ID を残すようにした (10) 条件抽出が2回失敗して offTopic に倒れたときだけ、禁止トピックを語で拾う安全網（`src/domain/forbidden.ts`）をかける (11) 閲覧用アカウントの権限と配色は判断待ちに積んだ
3. **2026-10-07: Supabase の作成（外部サービスの準備の1つ目）** — ユーザーの了承のもと Claude in Chrome で作成。リージョンは東京（ap-northeast-1）・無料プラン。作成時の「新しいテーブルを Data API に自動で公開する」は無効にした（Supabase の推奨で、権限はマイグレーションで anon には何も与えず必要な分だけ明示的に付ける設計と合うため）。Authentication の新規登録（Sign-ups）は無効（担当者は招待で作る）。マイグレーションは SQL Editor で適用し、テーブル 8・営業時間 7 曜日（水曜定休）・RLS ポリシー 17・RLS 有効 8 テーブルを確認した。キーは新形式の secret key（`sb_secret_…`）を service role として使う。データベースのパスワードはユーザーが入力（アプリでは使わない）
