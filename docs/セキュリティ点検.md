# セキュリティ点検（2026-10-25）

このデモをひな型にして発注を受けた製品を作る前に、セキュリティを点検した（意思決定ログ36）。

- やり方: 4 つの観点を並列に読んだ（入口と権限・LLM と個人情報と費用・設定と依存と公開物は Sonnet、製品にするときの盲点は Fable が一次情報を Web で確かめた）。どれも読むだけ。指摘は Claude（メイン）がコードと `npm audit` で裏取りし、確かめられたものだけを載せる
- 区分: **A** はいまの公開デモでも穴になるもの（直す）、**B** は製品にするときに変えるもの（ひな型の確認リスト）
- 状態の書き方: 「直した（PR 番号）」「これから直す」「判断待ち（引き継ぎ書7章）」「割り切る」

## 1. 結論

- **重大度「高」の穴は2つ**だった: Next.js 16.4.0 の既知の脆弱性（未認証で届く Server Actions の DoS を含む）と、回答の根拠検証の網の穴（URL・「確定しました」・国籍や収入についての断言を通す）。どちらも 2026-10-25 に直した（PR #42 と、その次の PR）。デモの穴（A）は A9・A16（割り切り）を除いて直した
- 骨格は堅い: Webhook の署名検証・Cron の秘密・8 つの表すべての RLS・service role の使い道・管理画面の権限の確かめ直し・プロンプトの区切り・ログに発話を出さないこと
- 弱いのは (1) **量の制限**（ボタンの連打・発話の長さ・利用者ごとの費用）と (2) **担当者アカウントを守る層**（MFA・失効・列単位の権限・ヘッダー）
- 製品にするときの最大の論点は**名義とプラン**: LINE のチャネルは発注者のプロバイダーの下に作り直すしかない（後から移せない）、Vercel Hobby は商用禁止、Supabase の無料プランはバックアップが無い。どれもお金と契約なので判断待ち

## 2. 堅かったところ（確かめて問題なかったもの）

- **Webhook**: 加工前のボディで HMAC-SHA256 を `timingSafeEqual` で照合し、署名の前に JSON を読まない。秘密が未設定なら 500。重複は `webhookEventId` の一意制約。グループ・ルームのイベントは無視（`src/lib/line/signature.ts`・`src/app/api/line/webhook/route.ts`）
- **Cron**: Bearer を SHA-256 にしてから定数時間で比べ、`CRON_SECRET` が未設定なら 500（`src/server/cronAuth.ts`）
- **RLS**: 8 表すべてで有効、`anon` には何も無い。`security definer` の関数は無く、全関数に `search_path = ''`。集計と削除の関数は `service_role` だけが呼べる。閲覧用（viewer）は `is_demo` の会話・メッセージ・仮受付・利用者だけを読め、書き込みのポリシーが無い
- **service role** を使うのは Webhook・Cron・`scripts/` だけ。管理画面のページ 6 本と Server Action 8 本はすべて `requireAdmin()` / `getStaffDeps()` を通る。`ADMIN_PREVIEW` は `NODE_ENV !== 'production'` でだけ有効
- **プロンプト**: 発話の `<` `>` を全角にしてから `<user_message>` で区切る（閉じタグで抜けられないことを実測）。LLM に渡るのは今回の発話・正規化済みのスロット・提示済みの物件だけで、会話の履歴も他の利用者のデータも渡らない。抽出の出力は enum・駅マスタ・提示済みの番号・営業日の検証で絞る
- **ログ**: `console.*` 31 か所に発話・表示名・LINE ユーザー ID は出ない。通知メールに表示名と LINE ユーザー ID は入らない
- **秘密**: 追跡しているファイルと全履歴に実キーの形は無い（`sk-ant-`・`sb_secret_`・JWT・`re_`・32 桁の16進など）。`NEXT_PUBLIC_` の環境変数は無い。XSS の入口になる `dangerouslySetInnerHTML` は定数のテーマ CSS だけ
- **CI**: `ci.yml` に秘密は渡らない。実 API の評価 `eval.yml` は手動実行だけで `permissions: contents: read`

## 4. 製品にするときに変えるもの（B・ひな型の確認リスト）

### 4.1 必ず変える

- **LINE のプロバイダーとチャネルを発注者の名義で作る**。チャネルは後から別のプロバイダーへ移せず、LINE ユーザー ID はプロバイダーごとに違う（LINE Developers の案内）。開発者は Admin / Member として招待してもらう。退任のときに外す手順も書く
- **Vercel を Pro にする**。Hobby は「非商用の個人利用のみ」で、対価を受けてサイトを作るのも商用に入る（Vercel Fair Use Guidelines）
- **Supabase を Pro にする**。無料プランは日次バックアップが無く、1 週間使われないと止まる。Pro は 7 日のバックアップ・漏えいパスワードの保護つき
- **プライバシーポリシーと利用規約を製品用に書き直す**（`src/app/_legal/content.ts`）。事業者名・住所・代表者・利用目的・開示などの請求の手続き・苦情の窓口・安全管理措置・**外国の名称**（Anthropic・Vercel・Resend は米国、Supabase の契約主体はシンガポール。サーバーは東京）・表示名や希望条件の保存期間。発注者が埋める欄を印にして、未記入ならビルドで落とす
- **Anthropic への送信を「外国にある第三者」として扱う**。商用の規約では学習に使わず、入出力は 30 日で消える。DPA は商用の規約に組み込まれているが、日本の法律（個人情報保護法 28 条の基準適合体制）として足りるかは未確認で、弁護士に確かめる。住宅の審査は Anthropic の利用ポリシーの高リスク領域なので、審査を禁止トピックにしている設計（不変条件3）を製品でも崩さない
- **発注者との契約に委託の中身を書く**: 再委託先（Supabase・Vercel・Anthropic・Resend・LINE）の承諾、安全管理措置、漏えいのときの通知（開発者 → 発注者を即時。発注者の報告期限は速報 3〜5 日・確報 30 日）、終わるときのデータと鍵の返却・削除
- **個人データの保存期間と削除の経路**: いまは LINE ユーザー ID・表示名・希望条件・仮受付・`webhook_events` が無期限で、ブロック（unfollow）も無視する。保存期間（例: 最後の発話から 1 年）を決めて Cron で消す、ブロックで消す（仮受付の対応中は保留）、管理画面に「この利用者のデータを削除」
- **担当者アカウントの守り**: TOTP の MFA を必須にして RLS で `aal2` を求める、退職のときは役割を外すだけでなくログインを止める（`admin-user.ts` に `--disable`）、JWT の有効期間を短くする（いまは役割を外しても最長 1 時間は効く）
- **担当者の DB の権限を列単位に絞る**。いまは担当者が自分のログインで Supabase の API を直接呼べ、`conversations` と `viewing_requests` のどの列も書き換えられる（`is_demo` を立てて実会話を閲覧用に見せる、確定の画面を通さずに `confirmed` にする、`messages` に AI の発言を偽造する）。`grant update (列, …)`・`with check (role = 'staff')`・`is_demo` と `line_user_id` を変えられなくするトリガー
- **デモ専用の仕組みを製品で落とす**: `DEMO_MODE`・閲覧用アカウント・毎朝のデモ会話の作り直し・ログイン画面の資格情報の表示。製品の本番で `DEMO_MODE` が立っていたら起動で落とす。閲覧用の役割は非公開の物件と備考まで読めるので、製品では作らない

### 4.2 変えたほうがよい

- **発注者ごとに別のデプロイ**（Vercel・Supabase・LINE チャネル・Anthropic のワークスペースを1組ずつ）。表にテナントの列が無く、マルチテナントにすると大きい。コードは1つで環境変数だけ差し替え、立ち上げの手順をスクリプトと確認リストにする
- **Anthropic のキー**: 開発者の組織に発注者ごとのワークスペースを作り、月額上限をそこに閉じる（前払いの残高切れで黙って止まる事故を発注者側で起こさない）。キーの失効日の運用は持ち込まない
- **新しい表と関数が既定で開かないようにする**: `alter default privileges … revoke`、マイグレーションを読んで「`create table` の後に `enable row level security`」「関数に `revoke … from public`」を確かめるテスト
- **`createSupabaseRepositories` の既定の引数（service role）をやめる**。渡し忘れると黙って RLS を迂回する。管理画面から `createServiceClient` を import するのを ESLint で禁じる。サーバー専用のモジュールに `import 'server-only'`
- **LINE 公式アカウントマネージャーから人が返信しても AI が止まらない**。返信は管理画面からだけ、と運用で決めるか、Chat Control（`mode: 'standby'`）を使う
- **ログイン**: Supabase の CAPTCHA 保護（Turnstile など）か、メールと IP ごとの回数制限。Supabase の Auth の設定（サインアップの無効・JWT の期限・パスワードの長さ）を `supabase/config.toml` か確認リストに残す
- **Resend は発注者のドメインのサブドメインから送る**（DKIM・SPF、DMARC 推奨）
- **LINE のチャネルアクセストークン**: 長期トークンは再発行した瞬間に古いものが無効になる。v2.1（期限つき・30 件まで共存）か、24 時間の猶予を使う差し替えの手順
- **利用者が書いた電話番号・メールを伏せる**（全角・漢数字も）。LLM・メール・保存の前に
- **物件データ由来の文字列**（名前・住所・備考）の長さと文字種を取込で確かめる（間接のプロンプトインジェクションと、備考の家主の個人情報）
- **同じ会話の並行イベントの排他**（楽観ロックか、同じ会話・同じ物件の未対応の仮受付を1件にする部分一意インデックス）
- **Webhook**: `destination` をボット ID と照合する。処理が途中で落ちたイベントの扱い（いまは処理の前に「処理済み」にする）
- **CI**: `npm audit --omit=dev --audit-level=high` を足す。action を SHA で固定し、`ci.yml` に `permissions: contents: read` を書く。`engines.node` を `>=22` に
- **Preview 環境**は本番と別の Supabase プロジェクトと別のキーにする
- **カスタムドメインでは HSTS を自前で出す**（`*.vercel.app` では Vercel が `preload` つきで付けるが、カスタムドメインでは付け方が弱くなる）
- **宅建業法・表示規約**: カードか免責の文に取引態様（媒介）・商号・免許番号を出せる設定。要否は発注者の宅建士に確かめる
- **`.claude/settings.json` の `deny`** を `.env` 系の全パターンと Edit / Write にも広げる（今回の点検役の提案。設定の変更なのでユーザーが決める）

### 4.3 デモのままでよい

- 不変条件 1〜14（LLM に SQL を書かせない・AI は確定しない・RLS が門・管理画面で service role を使わない・管理画面に LINE ユーザー ID を出さない）。製品の売りでもある
- 90 日の会話ログの削除と引き継ぎメモの原文の消去（期間は発注者と確かめる）、東京リージョン、通知メールに表示名と LINE ユーザー ID を載せない設計
- レート制限と1日の費用上限の仕組み（上限の値は発注者と決め直す）

## 5. 確かめていないこと

- 本番の HTTP の応答ヘッダー（本番に通信していない）
- Vercel の環境変数がどの環境に入っているか（特に `SUPABASE_SERVICE_ROLE_KEY` が Preview にあるか）と、Supabase の Auth の設定（サインアップの無効・Secure email change・JWT の期限）。どちらもユーザーの管理画面
- Next.js の DoS（A1）の攻撃の成立そのもの（advisory の記述による。試していない）
- Anthropic の DPA が日本の法律の基準適合体制として足りるか、LINE の1対1の返信が不動産の表示規約の「広告」に当たるか（弁護士・発注者に確かめる）
